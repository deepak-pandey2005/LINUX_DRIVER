# Chapter 24: SPI Bus Driver Subsystem

## 1. Architectural Overview of the Linux SPI Framework

The **Serial Peripheral Interface (SPI)** is a high-speed, synchronous, full-duplex serial communication bus widely used for interfacing microcontrollers with sensors, flash memory, displays, and ADCs.

In the Linux kernel, the SPI framework splits responsibilities cleanly into two layers:
1. **SPI Controller Drivers (Master/Host)**: Interface with the hardware SPI master peripheral (e.g. BCM2835 SPI on Raspberry Pi, i.MX ECSPI on NXP). Encapsulated by **`struct spi_controller`**.
2. **SPI Protocol/Client Drivers**: Implement the logical device communication protocol (e.g. SPI Flash MTD, SPI accelerometer, display controllers). Encapsulated by **`struct spi_driver`**.

```
+--------------------------------------------------------------------+
|                    User Space Applications                         |
|           (/dev/spi_sensor, spidev, Sysfs, ioctl)                  |
+--------------------------------------------------------------------+
                                  |
                                  v
+--------------------------------------------------------------------+
|               SPI Protocol Driver (struct spi_driver)              |
|        - Creates spi_transfer & spi_message descriptors            |
|        - Issues spi_sync() or spi_async() transactions             |
+--------------------------------------------------------------------+
                                  |
                                  v
+--------------------------------------------------------------------+
|                      Linux SPI Core Subsystem                      |
|        - Message Queueing & Pump Engine (kthread_worker)           |
|        - DMA Mapping & Buffer Alignment Validation                 |
+--------------------------------------------------------------------+
                                  |
                                  v
+--------------------------------------------------------------------+
|             SPI Host Controller (struct spi_controller)            |
|        - Implements transfer_one() or transfer_one_message()       |
|        - Drives SCLK, MOSI, MISO, and Chip-Select (CS) lines        |
+--------------------------------------------------------------------+
```

## 2. SPI Physical Signaling & Clock Modes

SPI uses 4 fundamental physical lines:
- **SCLK**: Serial Clock generated by the master.
- **MOSI**: Master Output, Slave Input.
- **MISO**: Master Input, Slave Output.
- **CS / SS**: Chip Select (active low by default) driven by the master to select an active slave.

### The 4 Standard SPI Clock Modes:
| Mode | Clock Polarity (`CPOL`) | Clock Phase (`CPHA`) | Description |
|---|---|---|---|
| **Mode 0** | 0 (Low when idle) | 0 (Sample on leading edge) | Data sampled on rising edge, shifted on falling edge |
| **Mode 1** | 0 (Low when idle) | 1 (Sample on trailing edge) | Data sampled on falling edge, shifted on rising edge |
| **Mode 2** | 1 (High when idle) | 0 (Sample on leading edge) | Data sampled on falling edge, shifted on rising edge |
| **Mode 3** | 1 (High when idle) | 1 (Sample on trailing edge) | Data sampled on rising edge, shifted on falling edge |

In kernel code, combine these flags:
```c
spi->mode = SPI_MODE_0; // (0 | 0)
```

## 3. The SPI Message & Transfer Model

Every SPI communication is composed of one or more **`struct spi_transfer`** blocks packaged into a **`struct spi_message`**.

```
+---------------------------------------------------------------+
|                      struct spi_message                       |
|   +-----------------------+       +-----------------------+   |
|   |  struct spi_transfer  | ----> |  struct spi_transfer  |   |
|   |  tx_buf: [Command]    |       |  tx_buf: NULL         |   |
|   |  rx_buf: NULL         |       |  rx_buf: [Data In]    |   |
|   |  len:    2 bytes      |       |  len:    64 bytes     |   |
|   +-----------------------+       +-----------------------+   |
+---------------------------------------------------------------+
```

### Full-Duplex Simultaneous Transfer:
Because SPI is intrinsically full-duplex, every clock cycle shifts one bit out on MOSI while shifting one bit in on MISO:
```c
struct spi_transfer xfer = {
    .tx_buf = out_buffer,
    .rx_buf = in_buffer,
    .len    = transfer_length,
    .speed_hz = 10000000, // 10 MHz
};

struct spi_message msg;
spi_message_init(&msg);
spi_message_add_tail(&xfer, &msg);

int status = spi_sync(spi_dev, &msg);
```

### Helper Functions:
- **`spi_write(spi, buf, len)`**: Transmits data without reading back.
- **`spi_read(spi, buf, len)`**: Reads data while sending zeros on MOSI.
- **`spi_write_then_read(spi, txbuf, txlen, rxbuf, rxlen)`**: Atomically writes command bytes and immediately reads response bytes with Chip Select held continuously asserted.

## 4. SPI Host Controller Driver Architecture

When writing an SPI host controller driver, implement `struct spi_controller`:
- `ctlr->bus_num`: Bus number identifier (or -1 for dynamic assignment).
- `ctlr->num_chipselect`: Number of hardware chip select lines available.
- `ctlr->mode_bits`: Bitmask of supported modes (`SPI_CPOL | SPI_CPHA | SPI_CS_HIGH`).
- `ctlr->transfer_one(ctlr, spi, xfer)`: Handler called per individual transfer.

---

## 5. Summary & Best Practices

- Always match client drivers with `struct spi_device_id` and Device Tree compatible strings (`of_device_id`).
- For multi-byte register transfers, prefer `spi_write_then_read` to prevent chip select glitching between address transmission and data reception.
- Ensure transfer buffers passed to `spi_sync()` are DMA-safe (allocated via `kmalloc`, not on the stack).
